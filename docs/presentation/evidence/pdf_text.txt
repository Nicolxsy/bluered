Cas_01 – Crear comunidad. Es el punto de entrada del sistema: un usuario funda un espacio donde luego
podrá compartir y descubrir conocimiento. De este caso dependen, de forma directa o indirecta, casi todos los
demás de esta sección.
Nombre: Crear comunidad
ID: Cas_01
Actores
Usuarios del sistema
Descripción
Espacio social para el intercambio de conocimiento con un propósito de intercambio de
dicha información de manera libre.
Precondición
La persona no puede tener un historial dudoso de sus intenciones.
Poscondición
Haber compartido conocimiento.
Escenarios
Primario
1. Se crea un perfil.
2. Se comparte conocimiento.
3. Se obtiene conocimiento.
4. Se genera debate.
Secundarios
1. El usuario tiene un historial dudoso.
Excepcionales
1. La comunidad no sigue el reglamento de la ley.
Autor
Joel Pérez
Cas_02 – Compartir conocimiento. Dentro de la comunidad creada, los usuarios publican y obtienen co-
nocimiento en distintos formatos. Este intercambio es el que, más adelante, da pie al debate (Cas_03) y a la
preservación de lo compartido (Cas_04).
Nombre: Compartir conocimiento
ID: Cas_02
Actores
Usuarios del sistema
Descripción
Acción de compartir conocimiento mediante distintos formatos.
Precondición
Tener un conocimiento que compartir.
Poscondición
Generación de discusión.
Escenarios
Primario
1. Se presenta conocimiento.
2. Se busca conocimiento.
3. Se obtiene conocimiento.
Secundarios
1. El conocimiento compartido no es el indicado.
2. El conocimiento obtenido no es el indicado.
3. El conocimiento buscado no existe.
Excepcionales
1. El conocimiento contiene información que vulnera las leyes.
Autor
Joel Pérez
Cas_03 – Generar debates. A partir del conocimiento compartido, los usuarios opinan y dialogan entre sí.
Estas discusiones son, a su vez, la materia prima de la que salen tanto las temáticas especializadas (Cas_05)
como los intereses comunes que reagrupan a las personas (Cas_06).
Nombre: Generar debates
ID: Cas_03
Actores
Usuarios del sistema
Descripción
Discutir sobre los conocimientos compartidos.
Precondición
Haber compartido conocimiento.
Poscondición
Se sectorizan las discusiones.
Escenarios
Primario
1. Una persona da una opinión sobre el conocimiento compartido.
2. Otras personas dialogan sobre la opinión y dan sus puntos de vista.
Secundarios
1. No se genera discusión sobre el tema tratado.
2. La discusión trata otros temas ajenos.
Excepcionales
1. Usan el espacio para dialogar sobre cómo vulnerar la ley.
Autor
Joel Pérez

Cas_07 – Iniciar sesión. Es el primer paso para participar en la red P2P: el cliente se autentica ante el servidor,
que es quien coordina la presencia y la búsqueda entre pares.
Nombre: Iniciar sesión
ID: Cas_07
Actores
Cliente, Servidor
Descripción
Permite al cliente autenticarse ante el servidor para acceder a la red P2P.
Precondición
El cliente tiene la aplicación abierta y una cuenta registrada.
Poscondición
El cliente tiene una sesión activa en el servidor.
Escenarios
Primario
1. El cliente ingresa sus credenciales.
2. El cliente envía la solicitud de inicio de sesión.
3. El servidor valida las credenciales.
4. El servidor crea la sesión y confirma al cliente.
Secundarios
1. (Paso 3) Las credenciales son incorrectas: el servidor rechaza la solicitud, informa el
error y el cliente puede reintentar.
2. (Paso 3) Ya existe una sesión activa con esa cuenta: el servidor informa y ofrece cerrar
la sesión anterior.
Excepcionales
1. (Paso 2) El servidor no está disponible: el sistema muestra un error de conexión y
permite reintentar más tarde.
2. (Paso 3) La cuenta está bloqueada por intentos fallidos: el servidor niega el acceso e
indica cómo recuperarla.
Autor
Joel Pérez
Cas_08 – Actualizar presencia. Una vez el cliente tiene sesión activa, informa periódicamente al servidor su
disponibilidad, para que otros clientes sepan si pueden contactarlo.
Nombre: Actualizar presencia
ID: Cas_08
Actores
Cliente, Servidor
Descripción
Permite informar al servidor el estado de disponibilidad del cliente (conectado, ausente
o desconectado) para que otros usuarios lo vean.
Precondición
El cliente tiene una sesión activa.
Poscondición
El servidor tiene registrado el estado actual del cliente.
Escenarios
Primario
1. El cliente cambia su estado o el sistema detecta un cambio de actividad.
2. El sistema envía el nuevo estado al servidor.
3. El servidor actualiza el registro de presencia del cliente.
4. El servidor confirma la actualización.
Secundarios
1. (Paso 1) El cliente permanece inactivo un tiempo: el sistema lo cambia automática-
mente a ausente.
2. (Paso 3) El estado enviado es igual al registrado: el servidor lo ignora y no genera
cambios.
Excepcionales
1. (Paso 2) Se pierde la conexión: el servidor, al no recibir señal del cliente en un tiempo
definido, lo marca como desconectado.
Autor
Joel Pérez

Nombre: Configurar carpetas
ID: Cas_09
Actores
Cliente
Descripción
Permite al cliente elegir las carpetas locales que compartirá con la red.
Precondición
El cliente tiene la aplicación abierta.
Poscondición
Las carpetas elegidas quedan guardadas en la configuración y se envían a indexar.
Escenarios
Primario
1. El cliente abre la sección de configuración de carpetas.
2. El cliente selecciona las carpetas que desea compartir.
3. El cliente confirma la selección.
4. El sistema guarda la configuración.
5. El sistema inicia la indexación de los archivos (Cas_10).
Secundarios
1. (Paso 2) El cliente quita una carpeta ya compartida: el sistema deja de compartirla
y elimina sus archivos del índice.
2. (Paso 2) La carpeta ya estaba configurada: el sistema informa y no la duplica.
Excepcionales
1. (Paso 4) El sistema no tiene permiso de lectura sobre la carpeta: informa el error y
no la agrega.
2. (Paso 4) La carpeta ya no existe: el sistema informa y la descarta de la configuración.
Autor
Joel Pérez
Cas_10 – Indexar archivos. El sistema recorre las carpetas compartidas y construye un índice de sus archivos,
que es la base sobre la que luego se resuelven las búsquedas (Cas_11 y Cas_12).
Nombre: Indexar archivos
ID: Cas_10
Actores
Sistema de Archivos Local
Descripción
Recorre las carpetas configuradas y genera un índice de los archivos (nombre, tamaño,
tipo) para poder buscarlos.
Precondición
Hay al menos una carpeta configurada para compartir.
Poscondición
Existe un índice actualizado con los archivos de las carpetas compartidas.
Escenarios
Primario
1. El sistema solicita al sistema de archivos local el listado de archivos de las carpetas
configuradas.
2. El sistema de archivos local devuelve la información de cada archivo.
3. El sistema construye o actualiza el índice.
4. El sistema informa que la indexación terminó.
Secundarios
1. (Paso 2) La carpeta está vacía: el índice queda sin entradas para esa carpeta y el
sistema lo informa.
2. (Paso 3) Los archivos ya estaban indexados y no cambiaron: el sistema los omite.
Excepcionales
1. (Paso 2) Un archivo no se puede leer: el sistema lo omite y lo registra en un aviso.
2. (Paso 2) El sistema de archivos no responde: el sistema cancela la indexación y la
reintenta más tarde.
Autor
Joel Pérez

Cas_12 – Transmitir búsqueda. El servidor reenvía la consulta a los clientes conectados y consolida sus
respuestas, devolviéndolas al cliente que inició la búsqueda.
Nombre: Transmitir búsqueda
ID: Cas_12
Actores
Servidor
Descripción
Envía la consulta del cliente al servidor para que la distribuya entre los clientes conectados
y devuelva los resultados.
Precondición
El cliente solicitó una búsqueda con sesión activa.
Poscondición
La consulta fue distribuida y los resultados consolidados fueron devueltos al cliente.
Escenarios
Primario
1. El sistema envía la consulta al servidor.
2. El servidor reenvía la consulta a los clientes conectados.
3. Los clientes responden con los archivos que coinciden.
4. El servidor consolida las respuestas.
5. El servidor devuelve los resultados al cliente que buscó.
Secundarios
1. (Paso 3) Ningún cliente responde con coincidencias: el servidor devuelve una lista
vacía.
2. (Paso 3) Se agota el tiempo de espera: el servidor devuelve los resultados parciales
recibidos hasta ese momento.
Excepcionales
1. (Paso 1) El servidor es inaccesible: el sistema informa la falla y cancela la búsqueda.

Cas_17 – Descargar archivo. Es el caso central de esta sección: el cliente local obtiene un archivo del remoto.
Para lograrlo depende de negociar la conexión (Cas_19) y puede apoyarse en la cola de espera (Cas_18) o en la
reanudación de descargas (Cas_22) si algo falla.
Nombre: Descargar archivo
ID: Cas_17
Actores
Local, Remoto
Descripción
Permite al usuario local descargar un archivo que comparte un usuario remoto.
Precondición
El usuario local seleccionó un archivo de un usuario remoto disponible.
Poscondición
El archivo completo queda guardado en el equipo local.
Escenarios
Primario
1. El usuario local selecciona el archivo y solicita la descarga.
2. El sistema negocia la conexión con el usuario remoto (Cas_19).
3. El sistema solicita el archivo al usuario remoto.
4. El usuario remoto envía el archivo por partes.
5. El sistema recibe las partes y verifica su integridad.
6. El sistema guarda el archivo y notifica que la descarga terminó.
Secundarios
1. (Paso 3) El usuario remoto no tiene slots de subida libres: el sistema agrega la descarga
a la cola de espera (Cas_18).
2. (Paso 4) La conexión se cae durante la descarga: el sistema intenta continuarla
(Cas_22).
3. (Paso 6) El archivo ya existe en el equipo local: el sistema pregunta si desea reem-
plazarlo o conservar ambos.
Excepcionales

7. Arquitectura Estructural y Diseño de Clases
El diseño de este sistema peer-to-peer (P2P) híbrido abandona los enfoques monolíticos tradicionales mediante
la aplicación estricta de Arquitectura Limpia (Hexagonal) y los principios SOLID. Se priorizó el modelado desde
la capa abstracta del dominio y los contratos de interfaces, delegando las implementaciones concretas (bases de
datos, sockets de red y algoritmos de ruteo) a la capa de infraestructura. Esto garantiza que la lógica central del
negocio sea completamente agnóstica a los detalles de transferencia y persistencia.
7.1.
Estructura del Cliente Peer (Capa P2P)
Para garantizar el Principio de Responsabilidad Única (SRP), la lógica del cliente se bifurca en dos orques-
tadores principales. Por un lado, la sincronización de presencia y metadatos se aísla de la transferencia binaria
de archivos. Además, se aplica sistemáticamente el Principio de Inversión de Dependencias (DIP): los módulos
de alto nivel no dependen de implementaciones concretas como RawTcpPeerTransport, sino de abstracciones
como IPeerTransport.
Como se observa en la Figura 53, la extensibilidad del sistema (Open/Closed Principle) se logra mediante patro-
nes de diseño del Gang of Four (GoF). El motor de red utiliza el patrón Strategy (INatTraversalStrategy) para
encapsular los algoritmos de perforación de NAT (UPnP, TCP Hole Punching) sin alterar el orquestador de des-
cargas. Para las búsquedas locales, se implementa un patrón Decorator (BloomFilterRepositoryDecorator)
que envuelve la base de datos local, permitiendo descartar consultas de red en memoria RAM con complejidad
de tiempo O(1) antes de incurrir en costosas lecturas de disco.

aplicación y la infraestructura.
7.2.
Estructura del Servidor Central
El Servidor Central actúa como el plano de control (Control Plane) de la red, manejando la señalización de
red sin intervenir en la transmisión de datos punto a punto. Su arquitectura está orientada a soportar una alta
concurrencia de conexiones persistentes (WebSockets o TCP crudo).
Figura 54: Arquitectura de clases del Servidor Central, aplicando el Principio de Segregación de Interfaces (ISP) para
desacoplar el enrutamiento de la persistencia de reseñas.
El diseño (Figura 54) demuestra el Principio de Segregación de Interfaces (ISP). Los repositorios están cla-
ramente delimitados: ISessionStore gestiona el estado efímero, mientras que IFileReviewRepository maneja
los datos transaccionales. El ruteo de paquetes implementa estrategias polimórficas a través de ISearchRoutingStrategy,
permitiendo transicionar de ruteos de difusión masiva (Broadcast) a enrutamientos filtrados por metadatos (Bloom
Filters) a medida que la red escala, sin reescribir los orquestadores centrales.
7.3.
Modelo de Datos y Persistencia Políglota
Una red P2P híbrida enfrenta cargas de trabajo asimétricas: transacciones ACID consistentes para el catálogo
global frente a mutaciones de estado de alta frecuencia para la presencia de red. Para resolver este cuello de
botella, el modelo adopta un enfoque de persistencia políglota.
47


===== PAGE 48 =====
Figura 55: Esquema dual de persistencia: estructuras de baja latencia en memoria (Redis/RAM) para sesiones y modelo
relacional (PostgreSQL) para la integridad de las reseñas.
La Figura 55 detalla este diseño híbrido. El estado volátil (sesiones, *heartbeats* y direcciones IP) se modela
en un clúster de memoria con mecanismos de expiración automática (TTL), liberando al servidor de costosos
procesos de bloqueo de filas (*row contention*). Simultáneamente, las entidades de dominio pesado, como el
catálogo de archivos indexados por su hash criptográfico SHA-256 y las reseñas de usuarios, se mantienen en
un motor relacional transaccional. Esto incluye la desnormalización estratégica de atributos como la calificación
promedio de los archivos, permitiendo operaciones de lectura O(1) fundamentales para enriquecer los resultados
de búsqueda en tiempo real sin sobrecargar el servidor con operaciones aritméticas redundantes.

9. Diagrama de Actividad con Particiones: Orquestación del Flujo de Descarga P2P
El comportamiento dinámico del sistema ante la solicitud de un recurso se modela mediante un diagrama de
actividades estructurado en particiones o carriles verticales (swimlanes). Esta división permite aislar con rigor
formal las fronteras de ejecución entre la capa de presentación del usuario, los orquestadores de aplicación del
cliente local, la capa de infraestructura de transporte/red y la entidad remota independiente que actúa como
servidor de datos.
En este flujo se corrige la asignación de responsabilidades de las arquitecturas cliente-servidor clásicas: la
verificación de la disponibilidad de slots de ancho de banda y la gestión de la cola de espera (queue policy) se
ejecutan estrictamente en el carril del Peer Remoto, ya que ningún cliente local tiene autoridad para arbitrar
recursos en una máquina externa. De igual forma, el mecanismo de perforación de enrutadores (NAT Traversal)
se delimita a la capa de red y únicamente se activa como contingencia si el handshake TCP directo resulta
bloqueado por cortafuegos residenciales.

10. Diagrama de Sistemas: Organización por Capas y Persistencia Políglota
Bajo los postulados de la Arquitectura Limpia (Clean Architecture), el sistema se estructura a alto nivel
mediante subsistemas y capas concéntricas organizadas por responsabilidades específicas. Esto garantiza que las
políticas de negocio centrales permanezcan totalmente desacopladas de los frameworks gráficos, los protocolos
de transporte y los motores de almacenamiento.
La descomposición arquitectónica contempla cuatro macro-sistemas:
